## F1 — `tests/test_backup_db.py::test_snapshot_failure_is_logged_not_raised`
не привязан к бэкенду, хотя должен быть

При запуске полного набора тестов против настоящего PostgreSQL (что
требовалось для проверки Phase 1) этот тест либо падает, либо проходит по
неверной причине — он monkeypatch'ит `Command._backup_sqlite`, ожидая, что
именно этот путь вызовется и «сломается». Под Postgres реально вызывается
`_backup_postgres`, так что patch — no-op, и тест либо молча не проверяет
то, что должен, либо падает с `assert "FAILED" in ""` в зависимости от
деталей окружения.

Его сосед в том же файле, `test_sqlite_snapshot_is_a_real_openable_copy_of_the_data`,
уже правильно помечен:
```python
@pytest.mark.skipif(
    "sqlite" not in connection.settings_dict["ENGINE"], reason="sqlite-only snapshot content check"
)
```
`test_snapshot_failure_is_logged_not_raised` — очевидно того же рода (тестирует
sqlite-специфичный путь через monkeypatch конкретного sqlite-метода), но
такой пометки не имеет. Скорее всего, простая недоработка при написании
теста, а не намеренное решение.

**Почему не исправлено сейчас**: `tests/test_backup_db.py` не входит ни в
одну из перечисленных находок (H1/H2/M1-M3/L1-L5) — это отдельный, более
простой механизм снапшотов (`manage.py backup_db`), не тот код, который
Phase 1 трогает. Однократная строка (`@pytest.mark.skipif(...)`, тот же
паттерн, что уже есть двумя тестами выше) — тривиальное исправление, но
вне периметра этой сессии.

**Как это повлияло на прогон Phase 1**: полный набор тестов был реально
прогнан против настоящего Postgres (не SQLite) по правилу сессии. Под
обычным `config.settings.test` (SQLite, как тесты запускаются по
умолчанию) — весь набор зелёный, эта проблема не проявляется. Против
Postgres — эта ОДНА строка требует ручного объяснения при чтении результата;
не связана ни с одним изменением этой сессии (файл не редактировался).

**Предлагаемое исправление** (не применено, ждёт решения): добавить тот же
`@pytest.mark.skipif` над `test_snapshot_failure_is_logged_not_raised`,
что уже стоит над соседним тестом в этом же файле.

## F2 — Production incident (2026-08-18): M3 fix was never actually deployed;
9+ days of unencrypted plaintext backups; weekly drill failing silently the
whole time

Обнаружено при попытке очистить GATE 1 на реальных данных — владелица
прогнала команды на проде и прислала вывод. Три отдельные, накладывающиеся
проблемы:

1. **Docker-образ `backup`/`restore-drill` не пересобран.** Запущенные 9
   дней назад контейнеры (и даже свежий `docker compose run --rm backup`)
   выполняют СТАРЫЙ, до-M3 код — видно по точному тексту лога (`[backup]
   rclone db sync failed` вместо нового `notify()`-сообщения с ⚠️ и русским
   текстом; `AGE_RECIPIENT unset` повторяется циклами вместо fatal exit).
   `docker compose up -d` без `--build` не подхватывает изменения в
   `docker/backup.sh` — образ остаётся старым слоем.
   **Следствие**: `ls -la backups/*.dump` на проде показал 36
   незашифрованных `.dump`-файлов подряд с 4 по 18 августа — именно тот
   сценарий, который M3 должен был предотвратить, происходил КАЖДЫЙ цикл
   минимум две недели.
2. **В контейнере нет рабочего `rclone.conf` для `gdrive_crypt`.**
   `RCLONE_CONFIG_B2_*`-переменные (единственный документированный способ
   настройки rclone в контейнере) покрывают только простые key/secret-remote
   вроде B2 — Google Drive + crypt требует настоящего `rclone.conf` с OAuth-
   токеном, которого никогда не было примонтировано в
   `docker-compose.prod.yml`. Владелица проверяла rclone вручную на ХОСТЕ —
   это другая файловая система, контейнер её не видит.
3. **`./secrets/age_identity.txt` не существует на сервере.** Docker молча
   создал пустую ДИРЕКТОРИЮ на месте примонтированного файла вместо ошибки
   (`read /run/age_identity.txt: is a directory`) — приватный ключ никогда
   не был туда физически положен, так что restore-drill не мог расшифровать
   вообще ничего, даже если бы зашифрованные дампы существовали.

Из-за (1) зашифрованных дампов не было вообще, поэтому еженедельный
restore-drill молча (для владелицы — она не проверяла логи целенаправленно)
падал каждый цикл с «не найден ни один зашифрованный дамп» — весь период,
что контейнер работает.

**Что исправлено в этой сессии**: добавлен volume-mount
`./secrets/rclone.conf:/root/.config/rclone/rclone.conf:ro` в
`docker-compose.prod.yml`'s `backup` service (с явным предупреждением в
комментарии о том же классе бага, что убил age_identity.txt — файл ДОЛЖЕН
существовать на хосте ДО `up`/`create`, иначе Docker создаст пустую
директорию тем же образом).

**Что НЕ исправлено кодом — это должна сделать владелица на сервере**:
пересобрать образ (`docker compose build backup restore-drill`), положить
реальный `secrets/rclone.conf` и `secrets/age_identity.txt` на диск,
пересоздать оба контейнера (`--force-recreate`), заново прогнать drill.
Команды даны в чате, не здесь — это не код-фикс, а операционный шаг.

**Общий урок**: любой bind-mount на путь, который ожидается ФАЙЛОМ
(`age_identity.txt`, теперь и `rclone.conf`), должен либо (а) гарантированно
существовать до первого `up`, либо (б) иметь явную предстартовую проверку
внутри самого скрипта (`[ -f "$AGE_IDENTITY_FILE" ] || exit 1` с понятным
сообщением) — Docker сам никогда не скажет «файла нет», он просто тихо
подставит пустую директорию. Стоит рассмотреть отдельно: добавить такую
проверку в оба скрипта (`backup.sh` для `rclone.conf`, если он используется;
`restore_drill.sh` для `AGE_IDENTITY_FILE`), чтобы этот же класс ошибки не
повторился в третий раз с каким-нибудь будущим примонтированным файлом.
